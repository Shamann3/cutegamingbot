# Дизайн: Косметические сундуки (лутбоксы) для Cute Farming

**Дата:** 2026-07-04
**Статус:** согласован по секциям в брейншторме, ожидает финальной вычитки
**Автор:** совместно с владельцем проекта

---

## 1. Цель и суть

Добавить в игру систему **косметических сундуков (лутбоксов)** как основной новый
источник монетизации и вовлечённости. Игрок покупает сундуки за Telegram Stars и
открывает их внутри игры с рулеточной анимацией (CS-style), получая косметику
(и иногда ресурсы). Вокруг сундуков строятся: осколки (мягкая валюта из дублей),
альбом коллекции с бонусами за сет, витрина в профиле и живая лента редких дропов.

Монетизация — **косвенная через Stars**: сундуки покупаются за звёзды, но открытие
развязано с оплатой через промежуточную сущность «ключ» (см. §4).

## 2. Ключевые решения (зафиксированы в брейншторме)

| Тема | Решение |
|---|---|
| Валюта покупки | Telegram Stars, **25★ за сундук**, счётчик количества (N сундуков = 25×N★) |
| Механизм оплаты (MVP) | Через существующий донат-бот (`CuteGamingBot`), fire-and-forget, модель «ключей». Нативные Stars-invoice — позже |
| Что падает | Косметика + КУТ/семена + функциональные предметы |
| Редкость | 3 уровня: Обычный / Редкий / Легендарный |
| Базовые шансы | 75% / 21% / 4% (данные, правятся из админки) |
| Гарантия (pity) | Нет, чистый рандом |
| Дубли | Превращаются в **осколки** (единая общая валюта) |

| Открытие | Рулетка по центру, лента едет **влево**, ~3.4с, торможение на выпавшем; легендарке — особый эффект |
| Пачка | x1 — полная рулетка; xN — итоговая сетка результатов |
| Размещение | Отдельная вкладка «Сундуки» с под-разделами Сундук / Коллекция / Осколки |

| Архитектура | Гибрид (C): косметика/сундуки — свои таблицы; КУТ/семена/функционал — существующие `users.balance` / `users.items` |

## 3. Архитектурный подход (C — гибрид)

Косметика фундаментально отличается от расходников: ей владеют один раз и
экипируют в слот, а не складывают стопкой. Поэтому косметика, осколки, каталог
сундуков и история открытий живут в **новых реляционных таблицах**. При этом
**не-косметические награды** (КУТ, семена, функциональные предметы) начисляются
в **уже существующие** `users.balance` и `users.items` — второй инвентарь не
изобретаем.

Существующая модель, на которую опираемся:
- `users.balance` (INT) — КУТ.
- `users.items` (TEXT/JSON, ключ→кол-во) — инвентарь расходников.
- `dex` — каталог игровых предметов.
- `admin_audit_log` — журнал действий администраторов (переиспользуем).

## 4. Модель оплаты и «ключей»

### Проблема
Текущий донат открывает **внешнего бота** `CuteGamingBot` со start-payload
`insert_{amount}_` и не возвращает в WebApp подтверждения оплаты (fire-and-forget).
Надёжного «оплатил → тут же крутанул» без доработки платёжного колбэка нет.

### Решение — промежуточная сущность «ключ от сундука»
1. Игрок в игре выбирает количество сундуков → цена 25×N★.
2. Игра открывает донат-бота тем же механизмом, но payload означает «выдать N ключей».
3. Донат-бот после оплаты начисляет игроку **N ключей** (тем же способом, каким
   сейчас начисляет КУТ).
4. Игрок возвращается в игру, видит «у тебя N ключей» и **открывает сундуки
   внутри игры** — мгновенно, с рулеткой и всеми эффектами.

### Хранение ключа
Счётчик в существующем `users.items['chest_key']` (как семена) — минимум нового кода.

### Свойства
- Переиспользует донат-бота как есть, ноль доработок платёжки на MVP.
- Открытие всегда мгновенно и надёжно, даже при задержке зачисления платежа.
- **Будущий переход на нативные Stars меняет только шаг 3** (ключи падают сразу
  после `successful_payment`); вся игровая логика открытия сохраняется.

## 5. Модель данных

Новые таблицы:

### `cosmetic_items` — каталог косметики
- `id` PK
- `code` TEXT UNIQUE — стабильный код
- `name` TEXT
- `emoji` / `asset` — визуал
- `slot` TEXT — `'plot' | 'background' | 'frame' | 'pet' | 'title'`
- `rarity` TEXT — `'common' | 'rare' | 'legendary'`
- `set_code` TEXT NULL — ссылка на серию
- `shard_cost` INT — цена прямой покупки за осколки
- `active` BOOL

### `cosmetic_sets` — серии для альбома
- `code` PK
- `name` TEXT
- `reward_type` TEXT — `'title' | 'frame' | 'kut'`
- `reward_value` TEXT/INT — что даётся за полный сет
- `active` BOOL

### `user_cosmetics` — владение и экипировка
- `user_id` BIGINT
- `cosmetic_id` INT
- `obtained_at` TIMESTAMPTZ
- `equipped` BOOL DEFAULT FALSE
- UNIQUE `(user_id, cosmetic_id)`
- Инвариант: не более одного `equipped=TRUE` на слот у игрока (следим в логике;
  можно усилить частичным уникальным индексом по вычисляемому слоту).

### `user_shards` — баланс осколков (единая валюта)
- `user_id` BIGINT PK
- `balance` INT DEFAULT 0
- (альтернатива — `users.items['shard']`, но отдельная таблица чище для аудита)

### `box_catalog` — типы сундуков
- `code` PK (MVP: один `cosmetic_box`)
- `name` TEXT
- `price_stars` INT DEFAULT 25
- `pool` JSONB — веса дропа: `item/rarity → weight`
- `active` BOOL
- Задел на сезонные сундуки: доп. поля `starts_at` / `ends_at` (в MVP не используются).

### `box_openings` — история/аудит каждого открытия
- `id` PK
- `user_id` BIGINT
- `box_code` TEXT
- `cosmetic_id` INT NULL (если выпала косметика)
- `reward_kind` TEXT — `'cosmetic' | 'kut' | 'item'`
- `reward_ref` TEXT/INT — что именно (item-ключ/сумма)
- `rarity` TEXT NULL
- `was_dupe` BOOL
- `shards_granted` INT DEFAULT 0
- `keys_spent` INT DEFAULT 1
- `override_applied` BOOL DEFAULT FALSE — сработал ли пер-игроковый override
- `opened_at` TIMESTAMPTZ
- Источник данных для ленты «кто что выбил» и для разбора споров.

### `player_chest_odds` — пер-игроковая подкрутка шансов
- `user_id` BIGINT PK
- `weights` JSONB — переопределённые веса (`rarity/item → weight`)
- `note` TEXT — причина
- `set_by` — админ
- `expires_at` TIMESTAMPTZ NULL — можно делать временным
- `created_at` TIMESTAMPTZ

Переиспользуем: КУТ-дроп → `users.balance`; семена/функционал → `users.items`;
`chest_key` → `users.items['chest_key']`.

## 6. Логика открытия (сервер решает, клиент показывает)

**Железное правило:** рандом и выдача — только на сервере. Клиент проигрывает
уже готовый результат. Иначе читы через подмену запросов.

### Поток `POST /api/chests/open { count: N }`
Одна транзакция, `SELECT ... FOR UPDATE` по игроку:
1. Проверить `users.items['chest_key'] >= N`, иначе ошибка.
2. Списать N ключей.
3. Для каждого сундука:
   - выбрать веса: если есть активная (не истёкшая) запись в `player_chest_odds` —
     использовать её (и пометить `override_applied`), иначе `box_catalog.pool`;
   - бросок → редкость → предмет внутри редкости;
   - если косметика новая — вставить в `user_cosmetics`; если дубль — начислить
     осколки (`user_shards += shard_value[rarity]`), `was_dupe=TRUE`;
   - не-косметические дропы — в `users.balance` / `users.items`;
   - записать строку в `box_openings`.
4. Коммит.
5. Вернуть массив результатов `[{reward, rarity, wasDupe, shardsGranted}, ...]`
   + новые балансы (ключи, осколки, КУТ).

Клиент рисует рулетку на **уже известном** результате: лента останавливается ровно
на выпавшем. x1 — полная рулетка; xN — итоговая сетка (по §8).

### Честность
- Экран «Шансы» с точными % — доступен всегда.
- `box_openings` — полный аудит на случай спора.
- Идемпотентность/анти-дабл: блокировка игрока в транзакции + защита от двойного
  клика на клиенте.

### Базовые веса (данные, не хардкод)
Обычный ~75%, Редкий ~21%, Легендарный ~4%. Внутри редкости — равномерно либо по
весам предметов. Финально балансируется по экономике.

### Осколки — курсы (заготовка, правятся из админки)
- За дубль: Обычный +5 / Редкий +25 / Легендарный +150.
- Прямая покупка: `cosmetic_items.shard_cost` (напр. Редкий 40, Легендарный 150).

## 7. Админ-панель

Встраивается в существующую архитектуру (`admin_content.py`, `admin_users.py`,
`admin_economy.py`, `admin_audit_log`).

- **Контент косметики/сундуков:** CRUD `cosmetic_items`, `cosmetic_sets`,
  `box_catalog` (веса пула, цены, активность) — по образцу `admin_quests.py` /
  `admin_content.py`. Правка весов/курсов без деплоя.
- **Пер-игроковая подкрутка шансов:** на карточке игрока блок «Шансы сундуков» —
  задать override (пресеты «щедрее/скупее» или ручные веса), срок действия (`expires_at`),
  причину. Всё пишется в `admin_audit_log`; факт срабатывания — в `box_openings.override_applied`.
- **Просмотр истории открытий** игрока (для поддержки/споров).

## 8. Интерфейс (макеты согласованы в визуальном компаньоне)

Файлы макетов: `.superpowers/brainstorm/1988-1783116820/content/`
(`roulette-center.html`, `result-reveal.html`, `collection-album.html`,
`profile-and-feed.html`).

### Вкладка «Сундуки» (новый таб в нижней навигации)
Под-разделы: **Сундук / Коллекция / Осколки**. Вверху — лента «кто что выбил».

**Экран «Сундук»:**
- Рулетка по центру (лента предметов, рамки по редкости, центральный указатель).
- В покое лента чуть дрейфует; при открытии разгоняется и тормозит влево на выпавшем.
- Счётчик количества (− N +), цена 25×N★, кнопка «Открыть ×N».
- Ссылки: Шансы / Осколки / Коллекция.

**Экран результата:**
- x1: предмет вылетает («поп»-анимация), баннер редкости, название, «✓ Новое» либо
  «Дубль → +осколки». Легендарке — особый эффект (затемнение, конфетти).
- xN: сводка «M новых · K дублей» + сетка предметов с рамками и бейджами НОВОЕ/ДУБЛЬ
  + строка о начисленных осколках.

**Экран «Коллекция»:**
- Предметы сгруппированы по сериям; у каждой — прогресс (3/4) и награда за сет.
- Собранные подсвечены рамкой по редкости; «надето»-бейдж на экипированных.
- Не открытые — серым силуэтом с ценой в осколках; тап → панель прямой покупки
  за осколки (с подсказкой «останется последний до бонуса за сет»).

**Экран «Осколки»:** баланс и, по сути, тот же каталог для прямой покупки.

### Профиль игрока (что видят другие)
- Аватар с рамкой-скином, титул, **витрина из 3 слотов** (игрок сам выбирает, какие
  редкие скины показать), превью фермы с надетым фоном/скином грядки, стрик и
  прогресс коллекции/сетов.

### Лента «кто что выбил»
- Живой поток **только редких и легендарных** дропов, с именем игрока, цветовой
  меткой редкости. Живёт вверху вкладки Сундуки. Источник — `box_openings`.

Экипировка скинов доступна из Коллекции и/или профиля (уточняется на этапе плана;
инвариант «один на слот» — в §5).

## 9. Риски и меры снижения (ВАЖНО)

Владелец принял осознанное решение делать **платный лутбокс за реальные деньги
(Stars)**. Ниже — риски и что закладываем, чтобы их снизить.

1. **Платный лутбокс = азартная механика.** Правила Telegram Stars и лутбокс-
   регуляторика ряда стран (Бельгия, Нидерланды и др.) ограничивают такие механики.
   Риск для платёжного канала/приложения — реальный.
   *Меры:* открытие развязано с оплатой через «ключи» (§4); осколки дают
   не-тупиковый путь к любому скину напрямую (снижает «чисто азартную» природу).

2. **Пер-игроковая подкрутка шансов vs публичные проценты.** Если на экране «Шансы»
   показаны 75/21/4, а конкретному игроку стоят другие веса — это расхождение с
   заявленным, что в ряде юрисдикций трактуется как введение в заблуждение строже,
   чем сам лутбокс.
   *Меры (на выбор владельца, зафиксировать при реализации):* показывать проценты
   как «базовые/ориентировочные»; либо трактовать override как **временный**
   инструмент (тесты/компенсации, с `expires_at`), а не постоянную практику. Полный
   аудит override в `admin_audit_log` и `box_openings.override_applied`.

3. **Возвраты и репутация.** Stars-платежи возвратные; недовольные крупными тратами
   бьют по отзывам.
   *Меры:* открытые шансы, история открытий (`box_openings`), понятный дисклеймер.

4. **Приватность в ленте.** Показываем имя игрока — виральнее, но это персональные
   данные.
   *Меры:* только редкие/легендарные события; при необходимости — переключатель
   обезличивания.

> Эти меры — часть дизайна, а не опция. Экран «Шансы», аудит открытий и модель
> «ключей» реализуются в MVP.

## 10. Границы MVP (что НЕ входит)

- Нативные Telegram Stars invoice (`sendInvoice` / `pre_checkout` /
  `successful_payment`) — **позже**; MVP на донат-боте через «ключи».
- Сезонные/лимитные сундуки — задел в `box_catalog` есть, механика ротации — позже.
- Осколки по редкости (разные типы) — на MVP одна общая валюта.
- Pity-система — нет.
- Торговля/дарение скинов между игроками — вне scope.

## 11. Открытые вопросы к реализации

1. Экипировка «один на слот»: инвариант через логику или частичный уникальный индекс.
2. Точный формат start-payload донат-бота для выдачи ключей (согласовать с владельцем
   донат-бота, который вне этого репозитория).
3. Финальные числа: цены `shard_cost`, курсы `shard_value`, стартовый пул `box_catalog.pool`.
4. Трактовка override (базовые проценты vs временный инструмент) — решение владельца (см. §9.2).
