# Craft Map — узлы-рецепты вместо безымянных линий

**Дата:** 2026-07-24
**Статус:** дизайн утверждён, готов к плану реализации
**Ветка:** `claude/craft-chain-visual-editor-6a5422`
**Предшественники:** Этап 1 (read-only карта), Этап 2 (создание/удаление, доступ, вёрстка)

## Проблема

Сейчас рецепт рисуется двумя независимыми линиями `ингредиент → результат`. Сам рецепт как сущность на карте не существует. Последствия:

1. **Непонятно, какая пара ингредиентов образует какой рецепт.** Если у предмета 3 рецепта, в него входит 6 линий, и сгруппировать их глазами невозможно.
2. **Параметры рецепта (шанс, количество на выходе) негде показать** — линия анонимна.
3. На реальных данных проекта это уже мешает: у предмета «Древесина» два рецепта, которые в панели свойств выглядят одинаково — `🌳 + 🪓 → 🪵 ×1` и `🌳 + 🪓 → 🪵 ×5`, потому что у Топора и Пилы похожие эмодзи. Различить их нельзя.

## Решение

Рисовать рецепт отдельным компактным узлом-«станком»: `ингредиенты → [⚗ 80% ×5] → результат`. Так делают промышленные планировщики; группировка ингредиентов становится однозначной, а параметрам рецепта появляется своё место.

Дополнительно: в текстовом представлении рецептов показывать **название + `#id`** вместо голых эмодзи.

## Принятые решения

| Развилка | Решение |
|---|---|
| Старый вид (прямые линии) | **Заменить полностью.** Одна модель, меньше кода и риска расхождений. Переключателя нет. |
| Счётчик «Связей» в статистике | **Оставить смысловые 30** (ингредиент→результат, 2 на рецепт), а не 45 визуальных рёбер. Число не «прыгает», смысл сохранён. |
| Подписи рецептов | **Название + `#id`** вместо эмодзи (эмодзи остаётся как иконка рядом). |

## Модель графа

### Узлы
- **Предмет:** `{ id: '<dexId>', kind: 'item', item }` — как сейчас.
- **Рецепт:** `{ id: 'r:<recipeId>', kind: 'recipe', recipe }` — новый.

Префикс `r:` гарантирует отсутствие коллизий с числовыми dex-id.

### Рёбра (3 на рецепт вместо 2)
| id | source → target |
|---|---|
| `<rid>:a` | `ingredientAId` → `r:<rid>` |
| `<rid>:b` | `ingredientBId` → `r:<rid>` |
| `<rid>:out` | `r:<rid>` → `resultItemId` |

### Индексы — БЕЗ ИЗМЕНЕНИЙ
`itemsById`, `recipesById`, `producedBy`, `usedIn`, `forward`, `backward` остаются отношениями **предмет ↔ предмет**. Это ключевое решение дизайна: вся аналитика продолжает работать в прежних терминах, узлы-рецепты существуют только в визуальной топологии.

## Что НЕ меняется

- **Детектор ошибок** (циклы, битые ссылки, дубли пар, неиспользуемые, недостижимые) считается по смысловым индексам → результаты идентичны текущим.
- **Глубина** остаётся 3 (макс.) и 1.7 (средняя) — не удваивается из-за промежуточных узлов.
- **Базовые / конечные предметы** — узлы-рецепты не имеют записей в `producedBy`/`usedIn`, поэтому естественно не попадают ни в одну из категорий.
- **«Связей»** — считается как количество отношений ингредиент→результат (2 на рецепт).

## Внешний вид узла-рецепта

Компактная карточка, заметно меньше карточки предмета:
- строка 1: `⚗ 80%` (шанс) и `×5` (кол-во на выходе);
- строка 2 (мелко): название рецепта или его `key`;
- ручка входа слева (от ингредиентов), ручка выхода справа (к результату);
- выключенный рецепт (`enabled: false`) — приглушённый, с пунктирным контуром;
- поддержка светлой и тёмной темы, как у остальных узлов.

## Взаимодействие

- **Клик по узлу-рецепту** → правая панель показывает рецепт: ингредиенты (название + `#id`), результат, шанс, количество на выходе, состояние вкл/выкл, кнопка «Удалить» (переиспользует существующее подтверждение и эндпоинт).
- **Подсветка цепочки** проходит сквозь узлы-рецепты автоматически (обход идёт по рёбрам) и подсвечивает их как часть цепочки.
- **ПКМ по узлу-рецепту:** показать цепочку, копировать ключ рецепта, удалить.
- **Авто-раскладка:** dagre получает меньший размер для узлов-рецептов; слои выстраиваются как предмет → рецепт → предмет.
- **Позиции:** координаты узлов-рецептов сохраняются в существующую таблицу `craft_map_positions` под ключом `r:<id>`. Колонка `item_id` имеет тип `TEXT`, поэтому **изменение схемы БД не требуется**.

### Краевые случаи (закрываются явно)

- **Фильтр по категории:** при скрытии категории узел-рецепт скрывается вместе со связанными предметами — иначе на холсте повисает «сирота» без входов и выходов.
- **Поиск:** узел-рецепта считается найденным, если найден его результат. Иначе получалась бы странная картина — предмет подсвечен, а производящий его рецепт затемнён.

## Текстовое представление рецептов (названия вместо эмодзи)

Везде, где рецепт выводится строкой (панель свойств предмета, панель рецепта), формат меняется с
`🌳 + 🪓 → 🪵 ×5`
на
`🌳 Дерево #290 + 🪓 Пила #301 → 🪵 Древесина ×5`

Эмодзи сохраняется как иконка, но однозначность обеспечивают название и `#id`.

## Тестирование

- **Обновляются:** тесты `buildGraph` (новая топология: узлы двух видов, 3 ребра на рецепт, префикс `r:`) и тесты `traverseChain` (цепочка теперь включает узлы-рецепты и ребро `:out`).
- **Должны пройти без изменений:** тесты `detectErrors` и `computeStats`. Это и есть доказательство, что смысловой слой не тронут — если они падают, значит индексы поехали.
- `viewState`, `craftKey`, `contentTabs` не затрагиваются.
- Проверка: полная сюита + сборка админки + живой прогон собранной админки в браузере.

## Вне области этой задачи

Не делаем (остаются в бэклоге идей): палитра неиспользуемых предметов, редактирование параметров рецепта, экономика/маржа по `price`, визуализация самого цикла, экспорт, undo/redo, количество ингредиентов (`×N`) и более двух ингредиентов — последнее требует изменения модели БД и игровой логики.
